01 · 11-1 · Стандартный аудит · Смысл опыта

В журнале виден успешный UPDATE таблицы HR.JOBS. Знаем ли мы, кто увеличил зарплату и с какого значения на какое?

Показать ответ

Запись позволяет установить пользователя и факт операции. В нашем опыте с обычным AUDIT_TRAIL=XML старые и новые зарплаты, SQL-текст и привязки отсутствовали. Поэтому только по этим записям нельзя определить направление изменения.

Старые и новые значения затем регистрируются отдельным триггером в занятии 11-2. Расширенный стандартный аудит может содержать SQL-текст, но универсального сохранения старых и новых значений строк не обеспечивает.

02 · 11-1 · Стандартный аудит · Действия в EM

Ты находишься на Home в EM. Где включить стандартный аудит с записью в XML? Опиши путь и значение параметра.

Показать ответ

Вход с административными привилегиями. Путь из задания: Server → Security → Audit Settings → Configuration → Audit Trail. Для AUDIT_TRAIL выбираем XML; изменение сохраняем в SPFILE.

Смотрим Show SQL, применяем изменение, штатно перезапускаем экземпляр и проверяем действующее значение. NONE отключает стандартный аудит.

ALTER SYSTEM SET AUDIT_TRAIL='XML' SCOPE=SPFILE;
03 · 11-1 · Стандартный аудит · Проверка результата

После сохранения XML в SPFILE команда SHOW PARAMETER AUDIT_TRAIL по-прежнему показывает DB. Почему? Что сделать дальше?

Показать ответ

В работающем экземпляре действует прежнее значение. AUDIT_TRAIL статический: нужен перезапуск экземпляра.

SHOW PARAMETER AUDIT_TRAIL

После перезапуска ожидаем XML. Статичность — причина перезапуска; сам выбор SCOPE=SPFILE не делает любой параметр статическим.

04 · 11-1 · Стандартный аудит · SQL

Напиши команду аудита INSERT, UPDATE и DELETE для HR.JOBS с настройкой BY SESSION.

Показать ответ
AUDIT INSERT, UPDATE, DELETE
ON HR.JOBS
BY SESSION;

В EM выбираем таблицу HR.JOBS, три операции и гранулярность Session, проверяем Show SQL, затем применяем. Без WHENEVER SUCCESSFUL / NOT SUCCESSFUL настраивается аудит успешных и неуспешных выполнений.

05 · 11-1 · Стандартный аудит · Наблюдение

Один сеанс выполнил пять UPDATE. Можно ли заранее обещать ровно одну запись из-за BY SESSION? Как проверить наш Oracle 11.2?

Показать ответ

Нельзя без проверки обещать ровно одну запись. В документации 11.2 есть оговорка об отдельных записях и при BY SESSION. Важны версия, режим и фактический вывод.

План: настроить аудит тестового объекта, выполнить пять операций в одном известном сеансе, завершить его и сопоставить записи по пользователю, объекту, времени и идентификатору сеанса.

В исходном опыте было по одному UPDATE от каждого из двух пользователей. Он не доказывает поведение пяти UPDATE. Здесь описываем проверку, автоматически ничего не запускается.

06 · 11-1 · Стандартный аудит · Пользователи и права

После GRANT ALL ON HR.JOBS TO AUDIT_USER сможет ли он изменять HR.EMPLOYEES, удалять строки из HR.JOBS или удалить саму таблицу HR.JOBS?

Показать ответ

На основании только этого предоставления прав:

  • Изменять HR.EMPLOYEES — нет.
  • Удалять строки из HR.JOBS — да, предоставлена DELETE.
  • Удалить чужую таблицу командой DROP TABLE — нет.

ALL здесь относится к объектным привилегиям на конкретную таблицу, а не ко всей схеме или всем системным полномочиям.

07 · 11-1 · Стандартный аудит · Транзакции

Сеанс A изменил MAX_SALARY, но не сделал COMMIT. Что увидит обычный SELECT в сеансе B? Что увидит сам A?

Показать ответ

В обычном режиме READ COMMITTED сеанс B увидит прежние зафиксированные значения. Сам A видит собственные незавершённые изменения.

После COMMIT новый SELECT в B сможет увидеть новые значения. Обычный SELECT не должен ждать завершения UPDATE только из-за блокировки изменённых строк.

COMMIT фиксирует транзакцию. ROLLBACK до фиксации отменяет её изменения, но не стирает запись стандартного аудита о выполненной операции.

08 · 11-1 · Стандартный аудит · Транзакции

AUDIT_USER увеличил MAX_SALARY всех должностей в 10 раз и сделал COMMIT. Как восстановить значения под HR? Поможет ли ROLLBACK?

Показать ответ

Обычный ROLLBACK уже не отменит зафиксированную транзакцию. В нашем контролируемом опыте:

UPDATE HR.JOBS
SET MAX_SALARY = MAX_SALARY / 10;
COMMIT;
SELECT * FROM HR.JOBS;

Сравниваем с сохранёнными исходными значениями. Деление подходит для этого опыта без посторонних изменений между двумя операциями; в произвольном происшествии исходные данные восстанавливают по достоверному источнику.

09 · 11-1 · Стандартный аудит · Журнал

Назови представление для просмотра XML-аудита. А для стандартного аудита в БД при AUDIT_TRAIL=DB?

Показать ответ

Для XML — DBA_COMMON_AUDIT_TRAIL: оно позволяет читать соответствующие XML-файлы из AUDIT_FILE_DEST.

Для стандартного аудита в БД — DBA_AUDIT_TRAIL. DBA_COMMON_AUDIT_TRAIL также объединяет несколько видов аудита.

SELECT * FROM DBA_COMMON_AUDIT_TRAIL;

В реальном анализе ограничиваем запрос по пользователю, объекту, времени и виду аудита. Для чтения нужны соответствующие права.

10 · 11-1 · Стандартный аудит · Похожая задача

Нужно регистрировать только успешные DELETE из HR.DEPARTMENTS. Напиши команду.

Показать ответ
AUDIT DELETE ON HR.DEPARTMENTS
BY SESSION WHENEVER SUCCESSFUL;

Для регистрации только неуспешных попыток — WHENEVER NOT SUCCESSFUL. Конструкции BY SUCCESS здесь нет.

11 · 11-1 · Стандартный аудит · Завершение опыта

Нужно удалить AUDIT_USER, отключить аудит HR.JOBS и вернуть AUDIT_TRAIL=DB. Напиши команды и укажи, после какой нужен перезапуск.

Показать ответ
DROP USER AUDIT_USER CASCADE;

NOAUDIT INSERT, UPDATE, DELETE ON HR.JOBS;

ALTER SYSTEM SET AUDIT_TRAIL='DB' SCOPE=SPFILE;

Перезапуск нужен для нового AUDIT_TRAIL. Для DROP USER и изменения объектных настроек NOAUDIT перезапуск не нужен. После запуска проверяем действующее значение DB.

DDL, например DROP USER, имеет неявные фиксации: не используй его как безобидную проверку посреди незавершённой транзакции.

Завершённые XML-файлы, относящиеся к опыту, переносим в E:\labs\adump; действующие и посторонние файлы не трогаем.

12 · 11-1 · Стандартный аудит · Отключение аудита

После перезапуска с AUDIT_TRAIL=NONE что будет с новыми стандартными записями, старыми записями и обязательным аудитом?

Показать ответ

Новые записи по обычным правилам стандартного аудита собираться не будут. Существующие записи автоматически не удаляются.

Обязательный аудит сохраняется: запуск и остановка экземпляра, подключения SYSDBA и SYSOPER. Это не запись всех команд каждого пользователя с ролью DBA.

FGA, аудит операций SYS через AUDIT_SYS_OPERATIONS и триггеры аудита значений управляются отдельно от AUDIT_TRAIL.

13 · 11-2 · FGA и значения · Понимание

Нужно узнать, кто выполнял UPDATE, кто читал SALARY и с какого значения на какое изменилась зарплата. Какие три механизма выбрать?

Показать ответ

Стандартный аудит — факт выбранной операции и участник. FGA — доступ к данным по политике, например чтение столбца SALARY. Триггер аудита значений — старое и новое значение конкретной строки при DML. Сам аудит не запрещает действие: доступ ограничивают привилегии.

14 · 11-2 · FGA и значения · SQL

Как создать политику только для SELECT с обращением к HR.EMPLOYEES.SALARY?

Показать ответ
BEGIN
  DBMS_FGA.ADD_POLICY(
    object_schema   => 'HR',
    object_name     => 'EMPLOYEES',
    policy_name     => 'B04_EMP_SALARY_SELECT',
    audit_column    => 'SALARY',
    statement_types => 'SELECT',
    enable          => TRUE);
END;
/

В упражнении — под SYS. audit_column выбирает контролируемый столбец, statement_types — вид команды. Условие по строкам не задано. Политика фиксирует подходящий доступ, а не определяет сама по себе, имел ли человек законное основание читать зарплату.

15 · 11-2 · FGA и значения · Проверка

Предложи три команды, которые покажут, что политика FGA реагирует именно на чтение SALARY.

Показать ответ
SELECT employee_id, salary FROM hr.employees WHERE employee_id = 200;
SELECT employee_id, last_name FROM hr.employees WHERE employee_id = 200;
UPDATE hr.employees SET salary = salary WHERE employee_id = 200;
ROLLBACK;

В известном сеансе HR первый SELECT соответствует политике. Второй не обращается к SALARY; UPDATE исключён явным statement_types=SELECT. Проверяем новые записи политики по сеансу и времени, а не общее число всех строк журнала. Это план проверки на учебных данных, страница команды не выполняет.

16 · 11-2 · FGA и значения · SQL

Где посмотреть, какой пользователь и каким SQL вызвал FGA?

Показать ответ
SELECT db_user, object_schema, object_name,
       policy_name, statement_type, sql_text
FROM dba_fga_audit_trail
WHERE policy_name = 'B04_EMP_SALARY_SELECT'
ORDER BY timestamp;

Для используемого хранения FGA в БД читаем DBA_FGA_AUDIT_TRAIL с необходимыми правами. Сопоставляем также время и сеанс. Для XML-хранения используется соответствующий XML-журнал, поэтому место просмотра зависит от audit_trail самой политики.

17 · 11-2 · FGA и значения · Механизм

Что означают AFTER UPDATE OF SALARY, FOR EACH ROW и :OLD/:NEW в триггере?

Показать ответ

AFTER UPDATE OF SALARY выбирает обновления, затрагивающие столбец SALARY. FOR EACH ROW означает запуск для каждой затронутой строки; :OLD и :NEW содержат её значения до и после изменения. В исходном примере IF :OLD.salary != :NEW.salary дополнительно отбирает фактическое изменение обычных ненулевых зарплат. UPDATE SALARY=SALARY не создаёт запись при этом условии. Это условие не является универсальной обработкой переходов с NULL.

18 · 11-2 · FGA и значения · Понимание

Что хранится в четырёх столбцах SYSTEM.AUDIT_EMPLOYEES? WHO — это HR?

Показать ответ

WHO — значение OS_USER, то есть имя пользователя ОС клиента; EVENT_DATE — дата и время; IPADDRESS — адрес клиента; WHAT — EMPLOYEE_ID, старая и новая зарплата. WHO в исходном триггере не равно имени пользователя Oracle по определению. Для пользователя БД можно отдельно получить SYS_CONTEXT('USERENV','SESSION_USER'). Добавление его в WHAT — явное расширение примера, а не часть исходного триггера.

19 · 11-2 · FGA и значения · Проверка

Ты изменил зарплату из SQL*Plus, но IP пустой. Как проверить аудит адреса и саму запись?

Показать ответ

Подключиться HR через Oracle Net и изменить зарплату известного сотрудника, затем COMMIT. Проверить WHO, IPADDRESS и WHAT в SYSTEM.AUDIT_EMPLOYEES, сопоставив сотрудника, время и значения. При локальном подключении без сети IP может отсутствовать. Сетевое подключение с того же компьютера может дать loopback, а не адрес другой машины.

20 · 11-2 · FGA и значения · Проверка

Изменили зарплату, откатили транзакцию. Должна ли остаться строка обычного триггера? Как правильно закончить опыт?

Показать ответ

В исходном триггере нет автономной транзакции: его INSERT — часть той же транзакции, что UPDATE. ROLLBACK откатит и зарплату, и строку таблицы аудита. Это отличается от стандартного аудита. Для опыта фиксируем изменение и запись, затем отдельным UPDATE восстанавливаем исходную зарплату и снова COMMIT. Проверяем точное восстановление; политика, таблица и триггер остаются результатом занятия.

21 · 12 · MANUAL и ASSM · SQL

Как создать TBSSPC: файл 50 МБ, рост по 10 МБ до 200 МБ, LOCAL, без ASSM?

Показать ответ
CREATE SMALLFILE TABLESPACE TBSSPC
DATAFILE 'spc1.dbf' SIZE 50M
AUTOEXTEND ON NEXT 10M MAXSIZE 200M
LOGGING
EXTENT MANAGEMENT LOCAL
SEGMENT SPACE MANAGEMENT MANUAL;

Это форма из задания; имя файла и его размещение предварительно проверяют. LOCAL и MANUAL отвечают за разные уровни управления пространством. Команда предназначена для подготовленной учебной среды.

22 · 12 · MANUAL и ASSM · Понимание

Файл создан с SIZE 50M AUTOEXTEND ON NEXT 10M MAXSIZE 200M. Что произойдёт при нехватке места и после удаления строк?

Показать ответ

Файл первоначально занимает 50 МБ. При необходимости Oracle автоматически расширяет его; NEXT задаёт минимальный шаг расширения 10 МБ. MAXSIZE=200 МБ — предел полного размера этого файла, а не ещё 200 МБ сверху. Требуется свободное место на диске. Удаление строк не уменьшает физический размер файла автоматически; достижение предела может привести к ошибке выделения очередного экстента.

23 · 12 · MANUAL и ASSM · Понимание

Чем EXTENT MANAGEMENT LOCAL отличается от SEGMENT SPACE MANAGEMENT AUTO? Что меняется относительно MANUAL?

Показать ответ

LOCAL управляет выделением и освобождением экстентов с помощью bitmap внутри табличного пространства. AUTO (ASSM) управляет свободным местом в блоках внутри сегмента с помощью bitmap; MANUAL использует списки свободных блоков. Поэтому LOCAL может сочетаться и с MANUAL, и с AUTO. ASSM — Automatic Segment Space Management; это не AUTOEXTEND файла.

24 · 12 · MANUAL и ASSM · Действия

Как задать исходную нагрузку и проверить, что она полностью завершилась?

Показать ответ

Подготовить SPCT с default tablespace TBSSPC и temporary TEMP, выдать заданные роли; создать таблицу SPCT. Исходный BAT запускает 15 SQL*Plus-процессов, каждый выполняет выданный lab_12_04.sql целиком. В нашем опыте 20 000 вставок на процесс дали 300 000 строк. Проверяем окончания всех процессов и сеансов, ошибки и число строк; один лишь спад графика не доказывает полный успех.

25 · 12 · MANUAL и ASSM · Порядок действий

В какой момент собирать статистику таблицы и делать два AWR snapshot? Что именно анализирует ADDM?

Показать ответ

До нагрузки: создать таблицу, собрать её статистику DBMS_STATS.GATHER_TABLE_STATS, создать первый AWR-снимок. Запустить нагрузку, снять график EM, дождаться полного завершения. Затем создать второй снимок и снова собрать статистику таблицы по заданию. ADDM анализирует производительность за интервал между снимками. Статистика оптимизатора о таблице и AWR-статистика производительности — разные данные.

26 · 12 · MANUAL и ASSM · График

Что означает AAS=2? Это два подключённых пользователя? Как связан AAS с DB time?

Показать ответ

AAS — среднее число активных сеансов: тех, кто работает на CPU или ожидает не в idle-событии. AAS = DB time / длительность интервала. Например, 120 секунд суммарного DB time за минуту дают AAS=2. Это не число всех подключений; неактивные подключения в эту активность не входят. CPU и категории ожиданий на графике различают.

27 · 12 · MANUAL и ASSM · Важная оговорка

Что на самом деле устанавливает DB_ACTIVITY_MIN=30? Почему в названии MIN?

Показать ответ
EXEC DBMS_ADVISOR.SET_DEFAULT_TASK_PARAMETER('ADDM','DB_ACTIVITY_MIN',30);

В проверенной реализации Oracle 11.2.0.1 это минимальная активность между двумя AWR-снимками для запуска ADDM: 30 секунд DB time. MIN означает minimum, не minutes. Это не время жизни базы, не период снимков и не 30-минутное окно анализа. В словах задания указано «30 мин.», что противоречит выданному SQL. Команду выполняли дословно; расхождение следует оговорить, а не молча менять 30 на 1800.

Точная единица подтверждена описанием параметра в установленной реализации 11.2; публичная справка DBMS_ADVISOR этот скрытый параметр отдельно не описывает.

28 · 12 · MANUAL и ASSM · EM

Где найти результаты ADDM и какую связь искать между Buffer Busy, SPCT и рекомендацией ASSM?

Показать ответ

Performance с обновлением 15 секунд показывает нагрузку; после второго снимка — Advisor Central → задача ADDM нужного интервала → View Result. Проверяем findings, затронутый объект SPCT и текст рекомендации. В опыте MANUAL появились Hot Objects и рекомендация ASSM. Если их нет, сначала проверяем нагрузку и интервал; разрешённые варианты усиления — 20 процессов и/или 40 000 итераций, с контролем завершения и места. Ожидаемый finding не подставляем вместо наблюдения.

29 · 12 · MANUAL и ASSM · Сравнение

Как честно сравнить MANUAL и ASSM? Можно ли считать, что ASSM всегда быстрее?

Показать ответ

Создать TBSSPC2 с SEGMENT SPACE MANAGEMENT AUTO, пересоздать таблицу там, собрать статистику и повторить ту же выбранную нагрузку с новой парой AWR-снимков. Сравнить сопоставимые SQL, ожидания и findings. В нашей итоговой паре было по 15×20 000 вставок: среднее время INSERT снизилось примерно с 0,001 до 0,00041 секунды, рекомендация Hot Objects исчезла. Это результат данного опыта, а не универсальная гарантия. Средний AAS и длительность AWR-окна сами по себе не равны скорости выполнения SQL.

30 · 12 · MANUAL и ASSM · Завершение

Что обязательно удалить перед темой 13? Чем DROP TABLE отличается от DROP TABLESPACE INCLUDING CONTENTS AND DATAFILES?

Показать ответ
DROP USER spct CASCADE;
DROP TABLESPACE tbsspc INCLUDING CONTENTS AND DATAFILES;
DROP TABLESPACE tbsspc2 INCLUDING CONTENTS AND DATAFILES;

Предварительно завершить свою нагрузку и проверить, что объекты и файлы именно учебные. DROP TABLE удаляет таблицу, но не табличное пространство и не его файл. CASCADE у DROP USER удаляет объекты пользователя; INCLUDING CONTENTS AND DATAFILES удаляет содержимое и файлы пространства. Проверяем отсутствие пользователя, обоих пространств и оставшихся процессов.

31 · 13 · Индексы · Механизм

После lab_13_01.sql все индексы EMPLOYEES стали UNUSABLE. Что произошло?

Показать ответ

Обслуживание включало ALTER TABLE HR.EMPLOYEES MOVE. Таблица получила новое размещение, ROWID строк изменились, а прежние индексы стали непригодны. UNUSABLE означает, что индекс нельзя использовать для доступа в этом состоянии. Объект индекса остаётся; данные таблицы не исчезают. Это отличается от невидимого индекса INVISIBLE.

32 · 13 · Индексы · SQL

Под HR выведи таблицы, имена и статусы всех индексов со статусом не VALID.

Показать ответ

FROM user_indexes
WHERE status <> 'VALID'
ORDER BY table_name, index_name;

USER_INDEXES показывает индексы своей схемы. В упражнении обнаружились все шесть индексов EMPLOYEES: MOVE повлиял на таблицу целиком, а не только на индекс первичного ключа. Для проверки другой схемы нужны соответствующее представление и права.

33 · 13 · Индексы · План

Почему поиск по EMPLOYEE_ID выполнил TABLE ACCESS FULL, хотя первичный ключ есть?

Показать ответ

Для поиска важен пригодный индекс, а не только наличие первичного ключа в схеме. Здесь индекс EMP_EMP_ID_PK был UNUSABLE, поэтому наблюдался полный просмотр таблицы. Но в общем случае TABLE ACCESS FULL не обязательно означает ошибку: оптимизатор может выбрать его по стоимости. Причину подтверждаем статусом индекса и фактическим планом.

35 · 13 · Индексы · EM

Как восстановить все найденные UNUSABLE-индексы и доказать успех?

36 · 13 · Индексы · План

Что изменилось после реорганизации и lab_13_07.sql? Зачем ещё обращаться к таблице после индекса?

Показать ответ

В новом плане появились INDEX UNIQUE SCAN по EMP_EMP_ID_PK и TABLE ACCESS BY INDEX ROWID. Индекс быстро находит ROWID строки по уникальному ключу; по нему читаются остальные нужные столбцы таблицы. Если всех выбранных столбцов нет в индексе, одного доступа к индексу недостаточно. В двух скриптах значения ключа различались, поэтому это прежде всего сравнение метода доступа, а не чистое измерение времени одного и того же SQL.

37 · 13 · Индексы · Проверка

После REBUILD все индексы VALID. Достаточно ли этого, чтобы сказать, что данные HR сохранены?

Нет. Статус индекса подтверждает его пригодность, но не равен проверке содержимого таблиц. Сравниваем строки и значения HR с исходным состоянием, проверяем ограничения и планы. В выполненной работе восстановлены исходные зарплаты, проверены данные HR и все шесть индексов EMPLOYEES. Число строк само по себе тоже не доказывает неизменность значений.

39 · 13 · Нагрузка · EM

Что смотреть в EM во время нагрузки и почему нельзя назвать CPU событием ожидания?

40 · 13 · Нагрузка · Причина ожидания

В Configuration показано log file switch (checkpoint incomplete). Что это означает?

Показать ответ

Для переключения redo требуется повторно использовать следующую группу, но необходимая контрольная точка ещё не завершена. Запись нужных изменённых блоков должна продвинуться, прежде чем группа станет пригодна для повторного использования. Это наблюдавшееся событие нашего опыта; одного названия недостаточно, чтобы доказать единственную физическую причину, например только медленный диск.

41 · 13 · Нагрузка · Процессы

Кто пишет изменённые блоки данных, а кто redo? Что показал I/O Function?

Показать ответ

DBWR записывает изменённые блоки из buffer cache в файлы данных. LGWR записывает redo из redo log buffer в online redo log. В выбранном интервале нашего I/O Function больше всего записей выполнял DBWR. Это результат графика; нельзя во всех нагрузках заранее обещать того же лидера. COMMIT не означает немедленную запись всех изменённых блоков таблиц DBWR.

42 · 13 · Нагрузка · Диагностика

Как определить SQL, который создаёт наибольшую активность? Можно ли ответить только «DELETE всегда медленный»?

Показать ответ

Top Activity: выбрать интервал нагрузки, посмотреть Top SQL, долю активности, текст SQL и связанные сеансы. В нашем наблюдении лидировал DELETE из нагрузочного скрипта; INSERT занимал меньшую долю. Это вывод по конкретному интервалу. Процент выборок активности не равен точному времени выполнения одной команды и не доказывает, что любой DELETE всегда медленнее INSERT.

43 · 13 · Нагрузка · EM

Опиши завершение нагрузки через EM. ORA-00031: session marked for kill — уже окончательный успех?

Показать ответ

Search Sessions → найти и заново идентифицировать свою пару SID/SERIAL#, пользователя и SQL → Kill Session, Immediate → проверить Show SQL и подтвердить. Затем проверить прекращение сеанса, транзакции и процесса нагрузки. ORA-00031 означает, что сеанс помечен для завершения; нужно дождаться фактического прекращения. Падение графика — дополнительный признак, а не единственная проверка.

В образце sid и serial# заменяются фактическими числами; случайную пару из примера использовать нельзя.

44 · 13 · Статистика и расписание · Понимание

Зачем после работ собирать статистику HR и OE? Это то же самое, что AWR?

Показать ответ

Статистика оптимизатора описывает объёмы и распределение данных, столбцы и индексы. Она помогает оценивать кардинальность и стоимость планов. После существенных изменений прежние оценки могут стать неточными. AWR хранит измерения работы экземпляра для анализа производительности; AWR-снимок не заменяет сбор статистики схемы. Свежая статистика помогает выбору плана, но сама по себе не гарантирует ускорение каждого SQL.

45 · 13 · Статистика и расписание · SQL

Напиши сбор статистики обеих схем с автоматической выборкой и статистикой индексов.

Показать ответ
BEGIN
  DBMS_STATS.GATHER_SCHEMA_STATS(
    ownname => 'HR',
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
    options => 'GATHER',
    cascade => TRUE);
  DBMS_STATS.GATHER_SCHEMA_STATS(
    ownname => 'OE',
    estimate_percent => DBMS_STATS.AUTO_SAMPLE_SIZE,
    options => 'GATHER',
    cascade => TRUE);
END;
/

AUTO_SAMPLE_SIZE позволяет Oracle выбрать объём выборки; это не обещание ровно 10% строк. cascade=TRUE включает статистику индексов. Вызов требует соответствующих прав и выполняется в задании через EM.

47 · 13 · Статистика и расписание · Расписание

Как настроить ежедневный сбор для двух схем в 21:00 по Москве, если гостевая ОС живёт в другом часовом поясе?

Показать ответ

В EM создать ежедневное задание, действие которого содержит оба GATHER_SCHEMA_STATS, включить его, не задавать дату окончания. Явно сопоставить часовой пояс расписания с Москвой. В нашей настройке 21:00 Москвы соответствует 18:00 UTC: использованы начало с зоной UTC и ежедневные 18:00. Менять часы Windows для этого не нужно.

FREQ=DAILY;BYHOUR=18;BYMINUTE=0;BYSECOND=0

Эта календарная строка задаёт UTC только вместе с соответствующей зоной START_DATE/расписания. Сама строка BYHOUR=18 часовой пояс не содержит.

48 · 13 · Статистика и расписание · Доказательство

Утром job включён, NEXT_RUN_DATE заполнен. Доказано ли, что вчера сбор автоматически состоялся?

Показать ответ

Нет. Нужна история именно ежедневного задания: запрошенное и фактическое время, SUCCEEDED, ERROR#=0, длительность и сведения об ошибках. Ручной Run Now другого задания не подтверждает срабатывание расписания. В нашем опыте проверили реальный вечерний автоматический запуск и результат следующим утром после 09:00 Москвы.

SELECT job_name, status, error#,
       req_start_date, actual_start_date, run_duration
FROM dba_scheduler_job_run_details
WHERE owner = 'SYS'
  AND job_name = 'B04_HR_OE_STATS'
ORDER BY log_date DESC;
49 · 13 · Статистика и расписание · Проверка

История показывает SUCCEEDED. Как убедиться, что статистика собрана и для HR, и для OE?

Показать ответ

Проверить неизменное действие задания с двумя процедурами и LAST_ANALYZED объектов обеих схем; сопоставить времена с интервалом запуска. В нашей проверке охвачены 7 таблиц HR и 10 таблиц OE. LAST_ANALYZED имеет тип DATE без часового пояса, а история Scheduler — значения с зоной: перед сравнением приводим времена к одной шкале.

SELECT owner, table_name, last_analyzed
FROM dba_tables
WHERE owner IN ('HR','OE')
ORDER BY owner, table_name;

Проверяем целевые таблицы с учётом их состояния и настроек. Если статистика заблокирована или задание упало, сохраняем ошибку и устраняем причину; ручной успешный запуск не выдаём за автоматический.
